1. L'OBJECTIF DU PROJET (Pourquoi avons-nous créé cela ?)
----------------------------------------------------------------------
En Algérie, la recherche scientifique est très active, mais il est souvent difficile pour les décideurs de mesurer l'impact réel des laboratoires, des équipes et des chercheurs. 
La "CERIST Biblio-Platform" est une plateforme web moderne et complète conçue pour résoudre ce problème. 

Son but est de faire le pont entre :
- Les données publiques de recherche (articles publiés, citations, H-index) via OpenAlex et PubMed
- La structure hiérarchique réelle de l'Algérie (Tutelle → Institution → Laboratoire → Équipe → Chercheur)
- Une gestion complète des utilisateurs avec 5 niveaux de rôles et permissions différentes

Au lieu que chaque chercheur calcule son "H-index" (sa note de performance) dans son coin, cette plateforme calcule automatiquement et dynamiquement les scores de groupes entiers sans faire d'erreurs (sans compter deux fois le même article écrit par deux chercheurs de la même équipe).

NOUVEAUTÉS CLÉS DE CETTE VERSION (V2) :
✓ Intégration OpenAlex + PubMed pour la recherche de publications
✓ 10 routers API avec 35+ endpoints
✓ 13+ pages React complètes avec dashboards interactifs
✓ Gestion complète des équipes et laboratoires avec hiérarchie explorable
✓ Rapports institutionnels pour les directeurs
✓ Système de notifications pour toutes les actions
✓ Recherche avancée avec opérateurs booléens (AND/OR)
✓ Synchronisation automatique des publications (harvester)
✓ Multi-tenancy sécurisé avec isolation des données par rôle

2. ARCHITECTURE GLOBALE (Comment ça marche à l'intérieur ?)
----------------------------------------------------------------------

Imaginez un très grand restaurant universitaire. Notre projet est divisé de la même manière :

A. LA FAÇADE / LA SALLE (Le "Frontend" - React.js + Vite)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
C'est ce que l'utilisateur voit sur son écran (les boutons, les graphiques, les tableaux, les formulaires). 
- Logique : React est conçu de façon "réactive". Si une donnée change, le graphique se redessine tout seul
- Technologies : React 19.2.0, React Router 7.13.1, Axios 1.13.6, Recharts 3.8.1, Vite 7.3.1
- 13+ pages complètes : Login, Register, Dashboard, TeamManagement, LabManagement, etc.
- 11 composants réutilisables : Header, Sidebar, ProtectedRoute, PublicationsChart, KPICard, etc.

B. LA CUISINE (Le "Backend" - Python & FastAPI)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
C'est le cerveau caché. Quand vous cliquez sur "Voir les statistiques", la salle envoie le serveur en cuisine.
- Framework : FastAPI 0.104.1 (ultra-rapide, async/await)
- Serveur : Uvicorn 0.24.0 (serveur ASGI)
- 10 routers avec 35+ endpoints pour toutes les opérations
- 6 services backend pour la logique métier (search, openalex, pubmed, bibliometrix, isolation, harvester)

C. LE GARDE-MANGER (La "Base de données" - PostgreSQL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
C'est où nous rangeons tout : les mots de passe cryptés, les noms des laboratoires, les articles, les utilisateurs, les rapports.
- PostgreSQL avec SQLAlchemy ORM 2.0.23
- 7 modèles de données : User, Institution, Laboratoire, Equipe, Publication, Rapport, Notification
- Intégrité des données garantie par Foreign Keys et contraintes
- Support Soft Delete pour l'historique

D. LES SCIENTIFIQUES EXTERNES (Bibliometrix via R + APIs)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
APIs externes :
- OpenAlex (https://api.openalex.org) : Source majeure de données de recherche, recherche d'auteurs, métadonnées enrichies
- PubMed (eutils.ncbi.nlm.nih.gov) : Données médicales, eSearch + eSummary

Calculs bibliométriques :
- Si Rscript 4.0+ disponible : utilise Bibliometrix via subprocess pour calculs avancés
- Fallback Python : H-index, G-index, I10-index calculés directement si R indisponible
- Agrégation groupe H-index pour les équipes avec déduplication automatique des publications

3. LA HIÉRARCHIE ET LES RÔLES (5 Niveaux Hiérarchiques)
----------------------------------------------------------------------

Le système est conçu avec un principe de "séparation stricte". Chacun ne voit que ce qu'il a le droit de voir (Multi-tenancy).

Niveau 1 : CHERCHEUR
└─ Rôle : Scientifique / Chercheur
   - Voit ses données personnelles uniquement
   - Publications et statistiques personnelles (H-index, citations)
   - Peut mettre à jour son profil
   - Routes accessibles : GET /api/users/{id}/publications, GET /api/users/{id}/stats
   - Nombre : Illimité par institution

Niveau 2 : CHEF_EQUIPE
└─ Rôle : Gère une Équipe
   - Peut ajouter/retirer des chercheurs de son équipe
   - Vue centralisée des statistiques de son équipe
   - Agrégation H-index groupe (publications fusionnées)
   - Comparaison performance des membres
   - Routes : GET /api/teams/{team_id}/statistics, GET /teams/{team_id}/members
   - Supervision : ~5-15 chercheurs par équipe

Niveau 3 : CHEF_LABO
└─ Rôle : Gère un Laboratoire
   - Crée les équipes et nomme les chefs d'équipe
   - Comparaison performance globale entre équipes
   - Vue macro du laboratoire avec drill-down possible
   - Routes : GET /hierarchy/laboratories, POST /hierarchy/laboratories
   - Supervision : ~2-5 équipes par labo

Niveau 4 : DIRECTEUR
└─ Rôle : Dirige une Institution (Université)
   - Gère tous les laboratoires d'une institution
   - Vue macro complète de l'institution
   - Crée les rapports institutionnels
   - SEUL niveau autorisé à créer des rapports (Rapport)
   - Routes : GET /director/statistics, GET /rapports, POST /rapports
   - Supervision : ~5-10 laboratoires par institution

Niveau 5 : TUTELLE
└─ Rôle : Gère au niveau national (Ministère)
   - Vue globale nationale de toutes les institutions
   - Droits suprêmes pour créer les institutions
   - Ne voit que les institutions sous sa tutelle
   - Routes : GET /api/institutions, POST /api/institutions
   - Nombre : 1-5 par gouvernement

Structure hiérarchique explorable :
```
TUTELLE (Ministère - Ex: DGRSDT)
    │
    ├─ DIRECTEUR
    │   │
    │   └─ Institution (Université 1)
    │       │
    │       ├─ CHEF_LABO
    │       │   │
    │       │   └─ Laboratoire 1
    │       │       │
    │       │       ├─ CHEF_EQUIPE
    │       │       │   │
    │       │       │   └─ Équipe 1
    │       │       │       │
    │       │       │       ├─ CHERCHEUR (Alice)
    │       │       │       ├─ CHERCHEUR (Bob)
    │       │       │       └─ CHERCHEUR (Charlie)
    │       │       │
    │       │       └─ Équipe 2
    │       │
    │       └─ CHEF_LABO (autre labo)
    │
    └─ DIRECTEUR (autre université)
        └─ Institution (Université 2)
            ...
```

4. SÉCURITÉ AVANCÉE (Techniques Implémentées)
----------------------------------------------------------------------

✓ Soft Delete (Suppression Douce)
  Quand un chef retire un chercheur de son équipe, il n'est pas effacé physiquement de la base.
  On change juste "is_active = False" ou on enlève le lien "equipe_id".
  Résultat : Historique des publications conservé à jamais.

✓ Multi-tenancy Sécurisé
  Tous les routers incluent des filtres automatiques par rôle.
  Exemple : Si un directeur demande "les labos", le backend ajoute automatiquement :
  WHERE institution_id = {current_user.institution_id}  ← FILTRE IMPLICITE
  Impossible de voir les données d'une autre institution.

✓ JWT Authentication (24 heures expiry)
  - Format : HS256 (HMAC with SHA256)
  - Token contient : user_id + expiration
  - Stocké dans localStorage du navigateur
  - Chaque requête inclut : Authorization: Bearer {JWT_TOKEN}
  - Signature empêche l'altération du token

✓ Cryptage des Mots de Passe (Bcrypt - 12 rounds)
  - Les mots de passe ne sont JAMAIS stockés en clair
  - Même si quelqu'un vole la base, les mots de passe sont inintelligibles
  - bcrypt.verify() compare sans jamais montrer le vrai mot de passe
  - 12 rounds = extrêmement long à "casser" par force brute

✓ Graphiques Avancés (Recharts)
  - Bar charts, Line charts, Scatter plots
  - Visualisations interactives avec drill-down
  - Classification des mots-clés (Moteurs, Niche, Émergents, Base)

✓ Cascading Hierarchy (Sélections en cascade)
  - Créer un compte : Choisir Institution → Déverrouille labos → Déverrouille équipes
  - Tout filtré en temps réel depuis le service d'isolation

5.1 LES 7 MODÈLES DE DONNÉES (models.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

① USER (Hub Central)
   - id (PK), nom, prenom, email (unique), password_hash
   - role ∈ {TUTELLE, DIRECTEUR, CHEF_LABO, CHEF_EQUIPE, CHERCHEUR}
   - institution_id (FK), labo_id (FK), equipe_id (FK)
   - openalex_id (liaison externe), is_active (soft delete)
   - Relations : institution, laboratoire, equipe, publications, rapports, notifications

② INSTITUTION
   - id (PK), nom, code, ville
   - tutelle_id (FK → User TUTELLE)
   - Contient : laboratoires, rapports, utilisateurs

③ LABORATOIRE
   - id (PK), nom, code
   - institution_id (FK → Institution)
   - Contient : équipes

④ EQUIPE
   - id (PK), nom, code
   - labo_id (FK → Laboratoire)
   - chef_equipe_id (FK → User avec rôle CHEF_EQUIPE)
   - Contient : utilisateurs (chercheurs)

⑤ PUBLICATION
   - id (PK), titre, auteurs, année, citées_par_count
   - user_id (FK → User)
   - author_id_openalex (liaison externe OpenAlex)
   - Source : OpenAlex ou PubMed

⑥ RAPPORT
   - id (PK), titre, contenu, date_création
   - institution_id (FK → Institution)
   - created_by (FK → User DIRECTEUR)

⑦ NOTIFICATION
   - id (PK), message, titre
   - user_id (FK → User)
   - is_read (Default: False)

7. FLUX COMPLET D'EXÉCUTION (Exemple Concret)
----------------------------------------------------------------------

Scénario : Un CHEF_EQUIPE veut voir les statistiques H-Index de son équipe

ÉTAPE 1 : React - Clic utilisateur
  └─ Utilisateur clique "Statistiques de mon équipe"

ÉTAPE 2 : React - Vérifier authentification
  └─ ProtectedRoute vérifie isAuthenticated + user.role
  └─ Si non autorisé → Redirection /login

ÉTAPE 3 : React - Faire requête API
  └─ axios.get("/team/42/statistics", {
       headers: { Authorization: "Bearer JWT..." }
     })

ÉTAPE 4 : FastAPI Middleware
  └─ CORS validation (origin OK?)
  └─ Route matching (/team/{team_id}/statistics)

ÉTAPE 5 : FastAPI - Décoder JWT
  └─ current_user = get_current_user() → Extraction user_id du token
  └─ Vérifier : user_id existe en BD?

ÉTAPE 6 : FastAPI - Vérifier autorisation
  └─ Vérifier : current_user.role == "chef_equipe"?
  └─ Vérifier : current_user.equipe_id == team_id?
  └─ Si refusé → HTTPException(403)

ÉTAPE 7 : FastAPI - Requête BD
  └─ SELECT * FROM equipes WHERE id = 42
  └─ SELECT * FROM users WHERE equipe_id = 42 AND is_active = True
  └─ SELECT * FROM publications WHERE user_id IN (...)

ÉTAPE 8 : FastAPI - Service bibliometrix
  └─ bibliometrix.calculate_group_h_index(publications_list)
  └─ Possibilité subprocess Rscript ou fallback Python
  └─ Retourner : h_index, g_index, i10_index, citations totales

ÉTAPE 9 : FastAPI - Formater réponse
  └─ return {
       "h_index": 8,
       "g_index": 12,
       "i10_index": 6,
       "total_publications": 25,
       "members": [ { "name": "Alice", ... }, ... ]
     }

ÉTAPE 10 : React - Recevoir + Afficher
  └─ setStats(response.data)
  └─ Page se redessine automatiquement (React)
  └─ Afficher : H-index = 8, graphique, tableau membres

✓ Integre deux sources majeures de données de recherche (OpenAlex + PubMed)
✓ Supporte une hiérarchie complexe à 5 niveaux avec isolation des données
✓ Fournit des calculs bibliométriques avancés (H, G, I10 indices)
✓ Offre un interface React moderne avec 13+ pages + 11 composants
✓ Expose 35+ endpoints API via FastAPI ultra-rapide
✓ Garantit la sécurité avec JWT + Bcrypt + RBAC + Multi-tenancy
✓ Persiste les données dans PostgreSQL avec intégrité relationnelle
✓ Supporte la synchronisation automatique des publications
✓ Génère des rapports institutionnels
✓ Fournit des notifications pour toutes les actions
