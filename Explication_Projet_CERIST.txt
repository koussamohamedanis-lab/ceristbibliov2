1. L'OBJECTIF DU PROJET (Pourquoi avons-nous créé cela ?)
----------------------------------------------------------------------
En Algérie, la recherche scientifique est très active, mais il est souvent difficile pour les décideurs de mesurer l'impact réel des laboratoires, des équipes et des chercheurs. 
La "CERIST Biblio-Platform" est une plateforme web moderne conçue pour résoudre ce problème. 

Son but est de faire le pont entre :
- Les données publiques de recherche (articles publiés, citations, H-index).
- La structure hiérarchique réelle de l'Algérie (Tutelle -> Institution -> Laboratoire -> Équipe -> Chercheur).

Au lieu que chaque chercheur calcule son "H-index" (sa note de performance) dans son coin, cette plateforme calcule automatiquement et dynamiquement les scores de groupes entiers sans faire d'erreurs (sans compter deux fois le même article écrit par deux chercheurs de la même équipe).


2. COMMENT ÇA MARCHE À L'INTÉRIEUR ? (L'Architecture Globale)
----------------------------------------------------------------------
Imaginez un très grand restaurant. Notre projet est divisé de la même manière :

A. LA FAÇADE / LA SALLE (Le "Frontend" - React.js)
C'est ce que l'utilisateur voit sur son écran (les boutons, les graphiques, les formulaires). 
-> Logique utilisée : C'est conçu de façon "réactive". Si une donnée change, le graphique se redessine tout seul sans avoir besoin de rafraîchir la page Web.

B. LA CUISINE (Le "Backend" - Python & FastAPI)
C'est le cerveau caché. Quand vous cliquez sur "Voir les statistiques", la salle envoie le serveur en cuisine. La cuisine récupère les ingrédients, prépare le plat (fait les calculs), et le renvoie.
-> Pourquoi FastAPI ? Parce que c'est l'un des moteurs les plus rapides au monde, capable de traiter des milliers d'articles scientifiques en quelques microsecondes.

C. LE GARDE-MANGER (La "Base de données" - PostgreSQL)
C'est là où nous rangeons tout : les mots de passe cryptés, les noms des laboratoires, et les articles.
-> Logique utilisée : On utilise des relations solides. Impossible de créer une "Équipe" si elle n'appartient pas à un "Laboratoire". Cela s'appelle l'intégrité des données.

D. LE SCIENTIFIQUE EXTERNE (Bibliometrix + Langage R)
C'est notre robot spécial. Pour les calculs mathématiques très compliqués (ex: Les cartes thématiques des mots-clés ou l'impact collaboratif), le Python passe le relais à un programme spécialisé en données (le langage "R"). Une fois fini, "R" redonne le résultat à "Python", qui le renvoie à votre écran.


3. LA HIÉRARCHIE ET LES RÔLES DE LA PLATEFORME
----------------------------------------------------------------------
Le système est conçu avec un principe de "séparation stricte". Chacun ne voit que ce qu'il a le droit de voir (Multi-tenancy).

Niveau 1 : Le Chercheur
-> Il connecte son compte à "OpenAlex" (la grande base de données mondiale de la recherche).
-> Il voit son H-index personnel, ses citations, et peut mettre à jour son profil protégé par un mot de passe obligatoire.

Niveau 2 : Le Chef d'Équipe
-> Il peut "recruter" (ajouter) des chercheurs de la base vers son équipe.
-> La plateforme fusionne les publications de toute son équipe pour calculer le vrai "H-Index de groupe" (Bibliometrie avancée).
-> Il a un "Radar" qui compare la performance de ses membres.

Niveau 3 : Le Chef de Laboratoire
-> Il crée les équipes et nomme les Chefs d'Équipe.
-> Il peut comparer la performance globale de ses différentes équipes.

Niveau 4 : Le Directeur d'Institution (ex: Le Recteur de l'Université)
-> Il gère tous les laboratoires.
-> Il a une vue "Macro" de l'université, mais peut "creuser" (Drill-down) pour voir un labo, puis une équipe, puis un chercheur spécifique.

Niveau 5 : La Tutelle (ex: Le Ministère - DGRSDT, MESRS)
-> Vue globale nationale. Ce rôle a les droits suprêmes pour créer les universités/institutions, mais ne voit que les institutions sous sa propre tutelle.


4. LA SYNTAXE ET LES DÉCISIONS INTELLIGENTES DU CODE (Soft Delete & Sécurité)
----------------------------------------------------------------------
Pour garantir un produit professionnel, des techniques avancées ont été codées :

- "Soft Delete" (Suppression douce) : Dans le code, si un Chef retire un membre de son équipe, le chercheur n'est *pas physiquement effacé* de la base de données. On change juste une petite variable "is_active" à "Faux", ou on enlève son étiquette d'équipe. Ainsi, l'université ne perd jamais l'historique des publications d'un chercheur.

- "Multi-tenancy sécurisé" : À chaque fois qu'une requête part en base de données, la logique SQL ajoute toujours un cadenas automatique : "Si ce directeur demande la liste des labos, montre M-O-I uniquement les labos OÙ institution_id = SON institution". Impossible de pirater ou de "voir" les labos du voisin.

- Graphiques Innovants (Recharts) : La bibliothèque de dessin ne fait pas que des camemberts. Elle fait des Nuages de dispersion (Scatter Charts) pour classer les mots-clés selon s'ils sont "Moteurs, De niche, Émergents ou De base".

- "Cascading Selects" : Lors de la création d'un compte, la logique est en cascade. On choisit l'Institution, ce qui débloque uniquement SES laboratoires, ce qui débloque ensuite uniquement SES équipes. Tout est filtré en temps réel depuis la "Cuisine".

----------------------------------------------------------------------
EN CONCLUSION :
La CERIST Biblio-Platform n'est pas juste un tableau d'affichage ; c'est un outil d'aide à la décision complexe capable d'isoler des données de manière hermétique, tout en fusionnant des bases de connaissances mondiales (OpenAlex) avec une analyse statistique poussée (Bibliometrix via R).

```python
from sqlalchemy.orm import relationship

class User(Base):

    id = Column(Integer, primary_key=True)  # Clé unique auto-générée
```

```python
from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
import jwt
from datetime import datetime, timedelta

router = APIRouter(prefix="/auth", tags=["Auth"])

# Endpoint de connexion
@router.post("/login")
def login(email: str, password: str, db: Session = Depends(get_db)):
    """
    L'utilisateur envoie un POST à /auth/login
    avec son email et mot de passe
    """
    user = db.query(User).filter(User.email == email).first()
    
    if not user or not bcrypt.verify(password, user.password_hash):
        raise HTTPException(status_code=401, detail="Email ou mot de passe incorrect")
    
    # Créer un JWT (jeton de confiance)
    payload = {
        "user_id": user.id,
        "exp": datetime.utcnow() + timedelta(hours=24)  # Expire après 24 heures
    }
    token = jwt.encode(payload, SECRET_KEY, algorithm="HS256")
    
    return {"access_token": token, "token_type": "bearer"}
```

Explication :
- POST /auth/login: React envoie l'email et le mot de passe
- bcrypt.verify(): Compare le mot de passe entré avec le hash stocké (sans jamais montrer le mot de passe!)
- JWT: Un petit ticket de confiance que React gardera. À chaque requête future, React l'envoie pour dire "C'est moi, j'ai le jeton!"

```python
def calculate_group_h_index(publications: list) -> dict:
    """
    Calcule le H-index d'une équipe/groupe
    """
    # Dédupliquer les publications (ne pas compter deux fois la même)
    merged = merge_publications_no_duplicates(publications)
    
    # Extraire les citations
    citations = [int(p.get('cited_by_count', 0)) for p in merged]
    sorted_cit = sorted(citations, reverse=True)
    
    # Calcul du H-index (via R via subprocess si disponible, sinon Python)
    h_index = 0
    for i, c in enumerate(sorted_cit, 1):
        if c >= i:
            h_index = i
        else:
            break
    
    return {
        "h_index": h_index,
        "total_publications": len(merged),
        "total_citations": sum(citations),
        "method": "bibliometrix_r ou bibliometrix_python"
    }
```

Explication (Cas pratique) :
Si une équipe a 5 publications avec :
- Article 1: 50 citations
- Article 2: 30 citations
- Article 3: 20 citations
- Article 4: 10 citations
- Article 5: 5 citations

H-index = 4, car 4 articles ont au moins 4 citations (50, 30, 20, 10).
L'article 5 a seulement 5 citations, donc on s'arrête.

```python
@router.get("/team/{team_id}/members")
def get_team_members(team_id: int, current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    """
    Obtenir les membres d'une équipe
    RESTRICTION: Seul le CHEF_EQUIPE ou CHEF_LABO de cette équipe peut voir cela
    """
    
    # Chercher l'équipe
    team = db.query(Equipe).filter(Equipe.id == team_id).first()
    if not team:
        raise HTTPException(status_code=404, detail="Équipe non trouvée")
    
    # SÉCURITÉ : Vérifier que l'utilisateur est autorisé
    if current_user.role not in ["chef_equipe", "chef_labo"]:
        raise HTTPException(status_code=403, detail="Accès refusé")
    
    # S'il est chef_equipe, vérifier qu'il est le chef de CETTE équipe spécifique
    if current_user.role == "chef_equipe" and current_user.id != team.chef_equipe_id:
        raise HTTPException(status_code=403, detail="Vous n'êtes pas le chef de cette équipe")
    
    # Retourner les membres
    members = db.query(User).filter(User.equipe_id == team_id).all()
    return [{"id": m.id, "nom": m.nom, "email": m.email} for m in members]
```

Explication de la logique de sécurité :
1. Qui appelle cette fonction ? C'est current_user (exploré via le JWT du token).
2. Quel est son rôle ? S'il est "chercheur", on refuse (403 - Forbidden).
3. S'il est "chef_equipe", on vérifie qu'il est le chef DE CETTE ÉQUIPE (pas une autre).
4. Enfin, on retourne les données.

PRINCIPES DE SÉCURITÉ INTENSES :
- Jamais de confiance aveugle. Chaque requête doit être validée.
- Principe du "Minimum Privilege" : Donne seulement ce qui est nécessaire.

```javascript
import { useState } from "react";
import axios from "axios";

function Login() {
  const [email, setEmail] = useState("");

  const [error, setError] = useState("");

      />

  );
```

6.4 COMPOSANT DE CONTEXTE POUR LA RECHERCHE : context/SearchContext.jsx
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Syntaxe :
```javascript
import { createContext, useContext, useState } from "react";

const SearchContext = createContext();

export function SearchProvider({ children }) {
  const [searchQuery, setSearchQuery] = useState("");
  const [searchResults, setSearchResults] = useState([]);
  const [isLoading, setIsLoading] = useState(false);

  const performSearch = async (query) => {
    setIsLoading(true);
    try {
      const response = await axios.get(
        `http://localhost:8000/search?q=${query}`,
        {
          headers: { "Authorization": `Bearer ${localStorage.getItem('access_token')}` }
        }
      );
      setSearchResults(response.data);
    } finally {
      setIsLoading(false);
    }
  };

  return (
    <SearchContext.Provider value={{ searchQuery, setSearchQuery, searchResults, performSearch, isLoading }}>
      {children}
    </SearchContext.Provider>
  );
}

export function useSearch() {
  return useContext(SearchContext);
}
```

Explication (Pourquoi SearchContext ?) :
Au lieu de passer les données de recherche de composant en composant en chaîne (compliqué), on crée un contexte GLOBAL qui n'importe quel composant peut utiliser.

Utilisation dans un composant :
```javascript
function MyComponent() {
  const { searchQuery, performSearch } = useSearch();
  return <div>Recherche actuelle: {searchQuery}</div>;
}
```

```javascript
  const handleUpload = async () => {
    if (!file) {
      setUploadStatus("Veuillez sélectionner un fichier");
      return;
    }

    const formData = new FormData();
    formData.append("file", file);

    try {
      await axios.post(
        "http://localhost:8000/upload/users",
        formData,
        {
          headers: {
            "Content-Type": "multipart/form-data",
            "Authorization": `Bearer ${localStorage.getItem('access_token')}`
          }
        }
      );
      setUploadStatus("Fichier uploadé avec succès!");
    } catch (error) {
      setUploadStatus("Erreur lors de l'upload");
    }
  };

  return (
    <div>
      <h2>Importer des utilisateurs (CSV)</h2>
      <input type="file" onChange={handleFileChange} accept=".csv" />
      <button onClick={handleUpload}>Importer</button>
      {uploadStatus && <p>{uploadStatus}</p>}
    </div>
  );
}
```

Explication :
- FormData: Classe JavaScript pour envoyer des fichiers.
- multipart/form-data: Le type MIME pour les fichiers.
- Le backend reçoit le fichier CSV et le traite ligne par ligne.

7. PATTERNS DE SÉCURITÉ AVANCÉS UTILISÉS
----------------------------------------------------------------------

7.1 JWT (JSON Web Token) POUR L'AUTHENTIFICATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Concept :
```
                CLIENT (React)                    SERVEUR (FastAPI)
                ════════════                      ══════════════════
    1. POST /login [email, password]  ──────────>
                                       <─────────  JWT "eyJhbGciOi..."
    2. localStorage.setItem('access_token', JWT)
    
    3. GET /profile [Header: Authorization: Bearer JWT] ──────>
                                        <────────  Profile data
```

Syntaxe JWT :
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJ1c2VyX2lkIjogMSwgImV4cCI6IDE2ODE5MzQ1NDd.
TJVA95OrM7E2cBab30RMHrHDcEfxjoYZgeFONFh7HgQ

Partie 1 (Header): Quel algorithme ? (HS256 = HMAC with SHA256)
Partie 2 (Payload): Les données (user_id, date expiration)
Partie 3 (Signature): Preuve que c'est vrai (seulement le serveur peut créer cette signature)
```

Pourquoi JWT est sûr ?
- La signature empêche quelqu'un de modifier le token (ex: changer user_id de 2 en 456).
- Expiration: Après 24 heures, le token est invalide.
- Sans mot de passe stocké dans localStorage (dangereux!), seulement le token.


7.2 HACHAGE DES MOTS DE PASSE AVEC BCRYPT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Concept :
```python
import bcrypt

# 1. Quand l'utilisateur crée un compte avec mot de passe "Azerty123"
password = "Azerty123"
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
# hashed = "$2b$12$abc...xyz" (complètement différent du mot de passe!)

# 2. On stocke CELA dans la base de données, pas "Azerty123"
user.password_hash = hashed

# 3. Quand l'utilisateur se connecte
entered_password = "Azerty123"
if bcrypt.verify(entered_password.encode(), user.password_hash):
    print("Connexion réussie!")
else:
    print("Mot de passe incorrect")
```

Pourquoi bcrypt ?
- Les mots de passe ne sont jamais stockés en clair.
- Même si quelqu'un vole la base de données, les mots de passe sont inintelligibles.
- 12 rounds: C'est extrêmement long à "casser" par force brute.


7.3 ISOLATION DES DONNÉES PAR RÔLE (Multi-tenancy)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Concept de filtre automatique en SQL :
```python
# Quand un DIRECTEUR demande "Donne-moi tous les labos"
@router.get("/laboratories")
def get_laboratories(current_user: User = Depends(get_current_user), db: Session = Depends(get_db)):
    if current_user.role == "directeur":
        # Ajouter un filtre automatique
        query = db.query(Laboratoire).filter(
            Laboratoire.institution_id == current_user.institution_id  # ← CADENAS!
        )
    elif current_user.role == "chef_labo":
        query = db.query(Laboratoire).filter(
            Laboratoire.id == current_user.labo_id
        )
    else:
        raise HTTPException(status_code=403, detail="Pas autorisé")
    
    return query.all()
```

Résultat :
- Un directeur de l'université X ne verra JAMAIS les laboratoires de l'université Y.
- Même si quelqu'un essaie d'écrire une URL malveillante : "/laboratory?id=999"
- Le filtre interceptera et refusera (user_institution ≠ lab_institution).


```javascript
const generateReport = async (format: 'pdf' | 'csv' | 'excel') => {
  const report = await api.post('/reports/generate', {
    format: format,
    type: 'team_statistics',  // ou institution, laboratory, etc.
    include: ['h_index', 'citations', 'publications', 'trends']

  link.click()
}
```
